【Q5.1 關鍵設計問答結論與實測數據解讀】

1. 每次請求為「立即失效」多付出的成本是多少？
   - (A) 已撤銷 Token 的快速失敗防禦成本 (Revoked Token Fast-Reject via Redis):
     * 當 Token 已被作廢（如登出、停用、改權限），Redis 藉由 O(1) 版本比對在 get_current_user 第一線立即拋出 401。
     * 實測攔截延遲: p50 僅 1.869 ms，p99 僅 2.713 ms，吞吐量高達 14642.0 RPS。
     * 與純無狀態 JWT 相比，僅多付出 +1.860 ms 的微秒/毫秒級開銷，且完全阻斷對 PostgreSQL 資料庫的查詢壓力。

   - (B) 有效 Token 在完整認證相依流程的成本 (Valid Token: get_current_user):
     * 在有效 Token 情境下，系統透過 Redis 驗證後，需由 Session 載入 User 實體（供下游業務端點使用並落實 DB 最終防線）。
     * 實測 p50 延遲為 41.269 ms，p99 延遲為 184.346 ms，吞吐量為 610.4 RPS。
     * 相對純無狀態 JWT，每次請求在相依層付出之總延遲成本約為 +41.260 ms (p50)，主要開銷源自 PostgreSQL 查詢連線池調度與 ORM 實體反序列化。

   - (C) 資料庫直查 / 快取未命中 (Direct DB Query Fallback):
     * 若完全不經 Redis 每次皆直接查庫，p50 延遲為 11.789 ms，吞吐量為 1310.2 RPS。
     * 由此可見 Redis token_version 機制的最大價值在於：「惡意或已作廢的大量請求能在 1~2 ms 內被 Redis 擋下，保護資料庫不被無效請求打垮」。

2. 快取如何與資料庫保持一致？
   - 登出、停用或角色修改時，在同一個 DB Transaction 提交 `user.token_version += 1`。
   - 交易成功後立即更新 Redis `user:{id}:token_version` 為最新版本，並設置 TTL 為 604800 秒 (7 天)。
   - 若寫入 Redis 失敗，系統觸發 fallback 執行 `redis.delete(key)`，強制後續請求回源查庫取得真實版本。
   - 驗證中介軟體在載入使用者實體後，一律以資料庫 `user.token_version` 作為最終 Single Source of Truth，若版本不符即刻抹除快取並回傳 401。

3. 最長不一致多久？
   - 正常情況：0 ms（資料庫 Commit 隨即以同步寫入 Redis，立即生效）。
   - Redis 寫入失敗但 Delete 成功時：0 ms（下一個請求即刻 Cache Miss 查庫並重新填入最新版本）。
   - 網路分區等極端異常（Redis 寫入與刪除皆超時失敗，且 Redis 仍保留舊值）：
     Redis 快取層本身之 TTL 設定為 604800 秒 (7 天)。然而，因 API 認證流程中一律會載入使用者實體並執行資料庫版本比對 (`user.token_version != token_version`)，故即使 Redis 保留陳舊快取，請求在抵達資料庫校驗關卡時便會即刻被攔截並修正快取，因此業務層面之實際不一致時間仍嚴格收斂為 0 ms。
